## Ronda 1

### Decisiones de diseño (las que el diseño no fija)
- **Estados HTTP del contrato de U0, no los del texto de la tarea.** El OpenAPI de `governance-service` (U0, intacto) fija `POST /v1/models` -> 200 con la `ModelVersion` y `approval`, `activation`, `freeze`, `frozen-resolution`, `decision`, `source-counts`, `validation-report` y `policies/{id}/approval` -> 204 (sin cuerpo). La tarea dice «(b) → 201» y el plan dice «`cro` aprueba → 200». No se cambia U0: la API responde 200 al registrar y 204 al aprobar. Es la discrepancia a revisar si el revisor prefiere 201/200 (tendría que cambiar el contrato).
- **Capa HTTP sin cliente oficial de Kubernetes.** `k8s_jobs.KubernetesJobs` habla con la API REST (`httpx`, 5 s) para no sumar un paquete al `uv.lock`. El doble de las pruebas es un `httpx.MockTransport` que guarda el manifiesto y lo devuelve en `GET`, así que se prueba el cliente real.
- **Orden del lanzamiento de validación.** Primero la transición (`registrado -> en_validacion` y la `ValidationRun`, con el `run_id` fijado por la API), después se crea el Job. Si Kubernetes falla, la corrida queda `fallido` y la versión `validacion_fallida` (motivo `launch_failed`), 503. `start_validation` ganó el parámetro `run_id`.
- **`run_id` del informe F32.** La ruta `PUT /v1/models/{id}/validation-report` no lleva `run_id`: es la corrida `validacion` `lanzado` más reciente de la versión; sin ella, 409.
- **Fuente propuesta = una transición** `- -> en_evaluacion` con el evento `evaluacion_iniciada` (BR-U4-13 dice «al proponer pasa a `en_evaluacion`»; BR-U4-17 un evento por transición). `propuesta` no se emite.
- **`start_source_comparison` no escribe evidencia**: la comparación no cambia el estado de ninguna versión (BR-U4-13). Solo inserta la `ValidationRun` `source_comparison` (con el `GLOBAL_LOCK`, que repite las condiciones) y crea el Job. La comprobación de los `InferenceService` (K01) va entre la lectura previa y el insert, sin sostener el lock durante la llamada de red.
- **`inference_service`** = `isvc-` + los 8 hex finales del `model_version_id` (`mv-<fecha>-<8 hex>`, `vectra_reference.package`); el texto de U4 dice «primeros 8 hex», pero el id empieza con `mv-<fecha>`.
- **`feature-spec` byte a byte.** La columna es `jsonb` (no conserva bytes). La API sirve el JSON canónico de U5 (`dump_json`: claves ordenadas, indent 2, UTF-8, salto final), que es idéntico al `feature_spec.json` de un paquete de U5. Una versión con otro formato de bytes no sería idéntica (candidata: guardar los bytes crudos en una columna nueva).
- **Medida de 60/64 KiB** de `freeze`: cuerpo completo de `POST /v1/entries` (con `actor`, `occurred_at`, etc.) serializado con `json.dumps` por defecto (cota por arriba de `httpx`).
- **`reason` de la API**: solo los del catálogo `ProblemReason` de U0 permitidos para `conflict_state` (`transition_pending`, `no_active_version`, `active_version_frozen`); los demás motivos internos de `model_fsm` no salen. No falta ningún `reason` en U0: no hubo que detenerse.
- **Fuera de la tarea (no hecho):** el cliente real del model-store (F47, S3) y el cableado de `build_app` por variables de entorno (chart, Paso 16); el RBAC `get inferenceservices` de K01 (chart).
